# GRPO vs GSPO Ablation Plan

这份计划只做一件事：把当前 `training/finqa_program_grpo.py` 与 `training/finqa_program_gspo.py` 放在同一个可比协议下，明确到底是哪一部分带来了提升，提升是来自 sequence-level importance sampling 本身，还是来自 reward 聚合方式、输出分布变化、训练不稳定性差异，抑或只是偶然的采样噪声。因为两条线共享同一批 RL 数据、同一套 verifier、同一个 executor、同一种 Program DSL，真正要控制的是初始化模型、采样预算、训练步数、评估口径和日志观测维度。如果这些条件不严格对齐，那么最终得到的差异结论就没有解释力。

最小可比实验应固定起点模型、训练集、验证集、`num_generations`、`temperature`、`top_p`、`max_completion_length`、batch size、gradient accumulation、learning rate、`beta`、LoRA 配置、量化配置和 checkpoint 保存/评估频率，只改变两点：第一，reward 是按 GRPO 的多头分项方式传给 trainer，还是按 GSPO-compatible 的 `core_score + format + evidence + length` 方式传入；第二，`importance_sampling_level` 是否为 `sequence`。如果这两个变化之外还有别的漂移，例如模型起点不同、一个实验启用了更强的梯度检查点或不同的 tokenizer，那么结果就不能解释成 GRPO 与 GSPO 的差异。

建议把 ablation 分成三个层次来做。第一层是 smoke 级别短跑，用来检查实现是否可比，长度建议是 50 到 100 step，目标不是看最终精度，而是确认日志路径、reward 曲线、可执行率和采样行为没有明显错误。第二层是中等长度对比跑，建议 300 step，与当前已有的 GSPO-compatible 训练长度对齐，用于观察 reward 平台、KL、sequence clipping、program exact match 和 benchmark 小样本结果。第三层才是正式长跑，建议 800 到 1500 step，只有在前两层确认日志与收敛模式正常后才值得投入。对当前任务，过早长跑没有价值，因为一旦 sequence-level 指标缺失，长跑只会放大不可解释性。

第一组实验建议就是当前最核心的主对比。实验 A 使用现有 `finqa_program_grpo.py` 配置，实验 B 使用现有 `finqa_program_gspo.py` 配置，二者共享同一 SFT 起点、同一 RL 数据文件、同一随机种子集合、同一训练步数和同一评估间隔。这一组要回答的问题非常直接：在不改 verifier contract 的前提下，GSPO-compatible 的 sequence-level 配置是否比 GRPO 的多头 reward 更容易把正确 program 推成高概率输出。如果这组实验结束后，GSPO 在 `program/exact_match_rate`、benchmark `executed_answer_accuracy` 和 `pass@1_greedy` 上没有稳定超过 GRPO，而只是训练 reward 更平滑，那么它对当前任务的价值就需要重新判断。

第二组实验建议进一步拆 reward 聚合与 optimizer 单位的影响。实验 C 可以保持 GRPO 的 trainer 配置，但人为把多头 reward 先在代码里压成一个 `core_score` 再传给 trainer，用来隔离“reward 是否压缩成单一程序正确性主项”本身的影响。实验 D 则保持 GSPO-compatible 的 sequence-level importance sampling，但把 `reward_program_core` 重新拆回多项日志可见的分项，仅作为记录，不改变最终优化标量。这样可以判断性能变化到底来自 reward 接口形态本身，还是来自 sequence-level ratio/clipping 机制。如果不做这组拆分，最终很容易把“单一 core reward 更稳”和“sequence-level policy update 更好”混为一谈。

第三组实验建议专门观察采样多样性与模式坍缩风险。因为两条线都使用 grouped sampling，如果 GSPO-compatible 在优化时更快地把概率质量压向少数模板，短期内 exact match 可能上升，但 `unique_program_ratio`、`has_program_rate` 或 benchmark 的 `pass@8` 可能下降。为此应设计固定 prompt 子集的周期性离线分析，比较同一个验证样本在 step 0、50、100、200、300 下的六条采样 completion，观察程序是否越来越单一、是否出现一种“格式很稳但程序错误稳定复现”的坏收敛模式。这一组不要求另写 trainer，只需要稳定保存若干 prompt-completion 样本并人工抽查。

TensorBoard 指标必须分成三层来看。第一层是 trainer 通用稳定性指标，也就是任何 RL 训练都应先确认的基本盘，包括 `reward`、`reward_std`、`kl`、`entropy`、`learning_rate`、`grad_norm`、`loss` 或 trainer 当前暴露的对应项。这里最重要的不是某个绝对值是否漂亮，而是趋势是否健康：如果 KL 长期几乎为零，reward 又很早平台化，往往说明更新过弱；如果 KL 在少数 step 突然抬升并伴随 exact match 下降，则说明策略偏移过猛。第二层是 clipping / importance sampling 相关指标。对 GRPO 线，至少保留现有 `clip_ratio/*`、`frac_reward_zero_std` 等默认项；对 GSPO-compatible 线，必须重点看 `sequence/response_clipped_fraction`、`sequence/response_low_clipped_fraction`、`sequence/response_high_clipped_fraction`。如果 GSPO 训练中这些 sequence-level clipped fraction 长期严格等于零，而 reward 与 benchmark 也没有改善，就说明 sequence-level 机制并未真正参与到有效约束中；如果 high-clipped fraction 很高且 `program/exact_match_rate` 下降，则说明更新可能过激。

第三层是 verifier-aware program 指标，这一层对当前任务最重要，也最应该作为主比较维度。无论是 GRPO 还是 GSPO，都应该稳定记录 `program/core_score`、`program/executable_rate`、`program/exact_match_rate`、`program/structure_score`、`program/argument_coverage`、`program/step_count_score`、`program/has_program_rate`、`program/unique_program_ratio` 和 `program/completion_words`。其中 `program/executable_rate` 用来判断模型是不是越来越会生成可运行程序，`program/exact_match_rate` 用来判断执行后的答案是否真正对齐 gold，`program/structure_score` 与 `program/argument_coverage` 用来判断模型是不是在向正确程序结构收敛，`program/unique_program_ratio` 则用来监控是否发生模式坍缩。对当前任务，`program/core_score` 上升但 `program/executable_rate` 不升，通常意味着 reward 构造里某些辅助项被模型利用；`program/exact_match_rate` 上升而 `unique_program_ratio` 断崖下降，则要警惕模型是否通过固定模板过拟合部分样本。

除了 TensorBoard，benchmark 指标必须作为最终判断标准，而且建议固定成一套小而稳的 protocol，不要每次切换口径。最少应在相同步数 checkpoint 上跑同一版 `evaluation/evaluate_financial_benchmarks.py`，报告 `executed_answer_accuracy`、`program_accuracy`、`program_parse_rate`、`program_execution_rate`、`structured_response_coverage`、`pass@1_greedy`、`pass@1_sampled`、`pass@4`、`pass@8` 和 `avg_prediction_chars`。如果当前 v3 口径中 `executed_answer_accuracy` 是主指标，那它就应该是 GRPO vs GSPO 比较的 headline metric；`program_accuracy` 则帮助判断是程序本身更接近 gold，还是只是执行结果凑巧正确；`program_execution_rate` 决定模型是否真正在学“可执行 program”；`pass@1_greedy` 反映高概率输出是否变强，而 `pass@4 / pass@8` 则反映采样空间里是否仍保留正确候选。如果 GSPO 提升了 `pass@1_greedy` 但压低了 `pass@8` 和 `unique_program_ratio`，这说明它可能在做更强的模式选择；如果 GRPO 的 `pass@8` 更高但 `pass@1_greedy` 低，则说明它更像是在维持正确候选存在，但还没把正确候选推成首选输出。

为了让结论更稳，benchmark 最好再做两层分桶。第一层按数据来源分成 `FinQA` 与 `ConvFinQA`，因为这两类任务对程序结构和多轮上下文依赖不完全相同，某条线可能只在单轮表文计算上更强，而在 ConvFinQA turn-level follow-up 上反而退化。第二层按 gold program 步数或难度分桶，例如 1 到 2 步、3 到 4 步、5 步以上。因为 sequence-level 优化如果真的更适合长程序，它的收益应该优先体现在长 program bucket 上；如果它只在简单样本上提升而在复杂样本上没有改善，结论就应该写成“对短程序更稳”，而不是笼统地说 GSPO 优于 GRPO。

建议最终采用如下判断顺序。先看实现正确性：日志目录是否一致、事件文件是否按预期写出、experiment config 是否完整记录超参和路径。再看训练过程：`reward`、`kl`、clipping、`program/executable_rate`、`program/exact_match_rate` 是否呈现健康趋势。最后看 benchmark：主指标 `executed_answer_accuracy` 是否提升，且这种提升是否在 `FinQA`、`ConvFinQA` 与不同 program 难度桶上具有一致性。如果某条线只是训练 reward 更高，但 benchmark 主指标不升，或者只在极少数桶提升，就不应把它认定为更优方法。

具体执行上，建议至少跑三组随机种子，例如 `42/43/44`，每组都在同样的 step 保存 checkpoint，并在 `100/200/300` step 做 benchmark。最终汇总表不要只写单次最好结果，而要报告每项指标的均值和标准差。对当前任务最值得放在 summary 表头的指标建议是 `executed_answer_accuracy`、`program_execution_rate`、`program_accuracy`、`pass@1_greedy`、`pass@8`、`program/exact_match_rate`、`program/unique_program_ratio` 和 `sequence/response_clipped_fraction`。如果 GSPO-compatible 在三种随机种子下都稳定提高 `executed_answer_accuracy` 与 `pass@1_greedy`，同时不显著损害 `pass@8` 和 `unique_program_ratio`，才能比较有把握地说 sequence-level 配置对当前任务有效；反之，如果它只改善训练曲线观感，而 verifier 和 benchmark 没有稳定受益，那么下一步应优先优化 reward 或数据，而不是继续在方法命名上前进。
