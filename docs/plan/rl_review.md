# FinQA 程序化 RL 评审记录

这份文档用于记录当前 `FinQA` 项目里程序化数值推理强化学习主线的算法判断、代码实现、reward 设计、训练流程和工程边界。当前主线已经不是传统意义上的 PPO，而是以 `training/finqa_program_grpo.py` 为核心的 GRPO 训练线，以及以 `training/finqa_program_gspo.py` 为核心的 GSPO-compatible sequence-level 训练线。仓库里虽然仍保留 `ppo_training.py` 和 `run_ppo.sh`，但针对 FinQA / ConvFinQA 这条可验证程序推理任务，真正承接实验的是 `run_finqa_program_grpo_v3.sh` 与 `run_finqa_program_gspo_v3.sh`，并且它们都从 `sft2_program_merged` 一类 program-SFT 检查点出发，而不是从通用对话模型直接起跑。

这条 RL 线的核心思路不是奖励“回答看起来是否自然”，也不是主要围绕偏好建模做文本风格优化，而是围绕可执行程序的正确性构造验证型 reward。对每一个训练样本，数据侧会提供 `input_prompt_raw`、`gold_answer`、`gold_program` 和 `reward_profile=program_numeric`。在 `prepare_dataset(...)` 中，代码首先检查这些字段是否齐全，然后直接执行 `gold_program`，要求其必须可执行，并且执行结果必须与 `gold_answer` 数值一致，否则该样本会被拒绝。这一点非常关键，因为它保证了后续 RL 所依赖的 verifier contract 本身是干净的，训练不会在脏标签或不可执行参考程序上浪费梯度。换句话说，这套 RL 不是先训练再想办法评估，而是先把“什么叫对”定义成一个可以执行、可以数值比较、可以自动验证的约束体系，再让策略优化围绕这个体系展开。

从训练流程上看，当前实现可以概括为一个相对清晰的闭环。首先从 json/jsonl 读取 RL 数据集，经过 `prepare_dataset(...)` 做字段校验、可执行性校验和 prompt 组装，形成带有 `prompt`、`gold_answer`、`gold_program` 的训练样本。然后加载 SFT 检查点、tokenizer、LoRA 配置和量化配置，构造 `GRPOTrainer` 或带 program diagnostics 的 trainer。在每个训练 step 内，对同一个 prompt 采样多条 completion，当前 shell 脚本中常见设置是 `num_generations=6`。随后从每条 completion 中解析出 `Program:`，必要时再解析 `Evidence:`，然后调用 executor 执行预测程序。如果程序缺失、写成 `N/A` 或执行失败，会立即得到负向或零奖励；如果程序成功执行，就继续计算执行结果与 `gold_answer` 的接近程度、预测程序与 `gold_program` 的结构一致性、参数覆盖、步数匹配、证据支持和输出长度正则项。所有 reward 项在 trainer 端按 `normalize_then_sum` 聚合，再进入 grouped relative policy optimization。GSPO 线与此共享同样的数据和 verifier，只是它把优化的主 reward 更明显地压缩到了 sequence-level core signal 上，并启用了 `importance_sampling_level=sequence`。

当前 GRPO 的 reward 设计是显式分项的。最基础的一项是程序可执行性奖励：如果 completion 中没有合法的 `Program:`，或者程序写成 `N/A`，就给 `-0.10`；如果成功执行，则给 `program_executable_reward_weight`，默认是 `0.15`。第二项是执行结果接近度奖励，它对成功执行的程序计算 `numeric_closeness(executed_value, gold_answer)`，再乘以 `program_execution_closeness_reward_weight`，默认是 `0.30`，这是当前最重要的 dense correctness signal 之一。第三项是程序结构相似度奖励，它通过 `program_similarity(pred_program, gold_program)` 比较预测程序和 gold 程序的计算骨架，这个相似度内部又由四部分组成：操作符 multiset F1 占 `0.45`，参数 multiset F1 占 `0.25`，公共前缀步骤比例占 `0.20`，步数接近度占 `0.10`，最后整体再乘 `program_structure_reward_weight=0.20`。第四项是参数覆盖奖励，通过对预测程序与 gold 程序的参数集合做 multiset F1，乘 `program_argument_coverage_reward_weight=0.12`，鼓励模型选择正确的数字、表项和中间变量。第五项是步数匹配奖励，只看预测程序与 gold 程序的步骤数差距，乘 `program_step_count_reward_weight=0.08`，用于抑制程序过短或过长的结构漂移。第六项是 exact match bonus，如果预测程序执行得到的数值与 `gold_answer` 在设定容差内完全一致，则再加 `program_exact_match_bonus_weight=0.05`。

除了这些与程序正确性直接相关的主 reward，GRPO 还加入了三类轻量正则。第一类是格式门控奖励 `reward_format_gate(...)`，它要求输出里至少出现 `Evidence:` 和 `Program:` 两个锚点，并鼓励 `Evidence:` 出现在 `Program:` 之前；如果输出中出现 `Reasoning:`、`Answer:`、`Normalized Answer:` 或 `Program: N/A` 这类当前 schema 不允许的锚点，则按项处罚。这个奖励的权重只有 `format_reward_weight=0.03`，地位明显低于可执行性和数值正确性，它的作用是把输出保持在当前任务定义的最小格式空间内，而不是驱动核心能力。第二类是证据支持奖励 `reward_evidence_support(...)`，只有在程序成功执行时才生效，它会抽取 `Evidence:` 中出现的数字，再与原始 prompt 中的数字集合做重叠统计，最多按 4 个数字封顶，最终乘 `evidence_reward_weight=0.04`。这项奖励不是严格的语义 grounding，只是一个低成本的 numeric grounding proxy，用来降低模型完全编造证据的概率。第三类是长度正则 `reward_length_regularizer(...)`，它依赖 `length_shape_score(...)`，偏好 80 到 160 词之间的 completion，超过 220 词则直接给 0，再乘 `brevity_reward_weight=0.02`。这一项主要用于避免输出不断变长，但它并没有把任务压缩成“越短越好”。

如果用论文式记号表达当前 GRPO 奖励，可以设输入 prompt 为 `x`，模型采样得到的 completion 为 `y=(y_1,...,y_T)`，从中抽取的预测程序为 `p=P(y)`，抽取的证据块为 `e=E(y)`，gold 程序为 `p*`，gold 数值答案为 `a*`，程序执行结果为 `v=Exec(p)`。再定义指示函数：如果 `p` 存在且不等于 `N/A`，则 `I_prog(y)=1`，否则为 0；如果 `Exec(p)` 成功，则 `I_exec(y)=1`，否则为 0；如果 `v` 与 `a*` 在容差内数值相等，则 `I_exact(y)=1`，否则为 0。定义 `C(v,a*)` 表示数值接近度，`S(p,p*)` 表示程序结构相似度，`A(p,p*)` 表示参数覆盖得分，`T(p,p*)` 表示步数相似度，`G(y)` 表示格式得分，`E(e,x)` 表示证据数字重叠得分，`L(y)` 表示长度形状得分，则各分项可以写成 `R_exec(y)=w_exec` 当 `I_exec(y)=1`，否则 `R_exec(y)=-0.10`；`R_close(y)=w_close * C(v,a*) * I_exec(y)`；`R_struct(y)=w_struct * S(p,p*) * I_prog(y)`；`R_arg(y)=w_arg * A(p,p*) * I_prog(y)`；`R_step(y)=w_step * T(p,p*) * I_prog(y)`；`R_exact(y)=w_exact * I_exact(y)`；`R_fmt(y)=w_fmt * G(y)`；`R_evd(y)=w_evd * E(e,x) * I_exec(y)`；`R_len(y)=w_len * L(y)`。这样总 reward 就是 `R_GRPO(y)=R_exec(y)+R_close(y)+R_struct(y)+R_arg(y)+R_step(y)+R_exact(y)+R_fmt(y)+R_evd(y)+R_len(y)`。在实现里，这些 reward 作为多个 head 分别传给 trainer，再由 `multi_objective_aggregation=normalize_then_sum` 聚合。

GSPO 线继承了同样的问题定义和 verifier 约束，但 reward 接口被重新组织。当前 `finqa_program_gspo.py` 并不是一个完全自定义的 full GSPO trainer，而是一个 GSPO-compatible sequence-level 配置；它仍然使用 `GRPOTrainer`，但显式设置了 `importance_sampling_level=sequence`，同时保留 `loss_type=dapo`、`multi_objective_aggregation=normalize_then_sum` 和 `scale_rewards=none`。与 GRPO 相比，它最核心的变化不是数据或 evaluator，而是把程序正确性的主信号压成了一个 `reward_program_core(...)`。在这项 reward 中，如果 `Program:` 缺失、写成 `N/A` 或执行失败，就直接返回 `-0.10`；一旦执行成功，就把程序可执行性、执行结果接近度、结构相似度、参数覆盖、步数匹配和 exact match bonus 全部加总成一个 `core_score`。因此可以把 GSPO 的核心主项写成 `R_core(y)=w_exec + w_close*C(v,a*) + w_struct*S(p,p*) + w_arg*A(p,p*) + w_step*T(p,p*) + w_exact*I_exact(y)`，前提是 `I_prog(y)=1` 且 `I_exec(y)=1`，否则 `R_core(y)=-0.10`。GSPO 的总 reward 则变成 `R_GSPO(y)=R_core(y)+R_fmt(y)+R_evd(y)+R_len(y)`。从工程意图看，GRPO 是显式多头 reward，便于单项调权和逐项排查；GSPO 则是把 verifier 主信号压缩成更统一的 sequence-level task reward，再把格式、证据和长度作为辅助项保留下来。

这也是当前两条训练线最本质的区别。GRPO 更像一个分项透明的 program-RL baseline，适合确认 reward 各部分是否定义合理、是否存在某一项权重明显失衡的问题。GSPO-compatible 线的目标则是让优化单位与 reward 单位更加一致，因为这里真正关心的是整条 response 对应的程序是否可执行、执行值是否正确、结构是否稳定，而不是单个 token 的局部风格是否自然。也正因为如此，当前不能把 `finqa_program_gspo.py` 简单声称为 full GSPO。它已经采用了 sequence-level importance sampling 配置，并增加了 `ProgramDiagnostics` 与 `ProgramDiagnosticGRPOTrainer` 来记录 `program/core_score`、`program/executable_rate`、`program/exact_match_rate`、`program/structure_score`、`program/argument_coverage`、`program/step_count_score`、`program/has_program_rate`、`program/unique_program_ratio`、`program/completion_words`，同时把 TRL 的 sequence clip 指标映射为 `sequence/response_clipped_fraction` 等更直观的名字，但它还没有完全自定义论文里的 response-level loss。当前更准确的说法是：它是一条利用 TRL sequence-level importance sampling 的 GSPO-compatible program RL 线，而不是从头实现的一版 full GSPO。

从最近训练状态的现象来看，GRPO 与 GSPO-compatible 都已经能稳定运行，但仅凭旧的 trainer 默认指标还不足以判断哪条线真正更优。此前观测到的 `kl` 很低、`clip_ratio/*` 长期为零，只能说明 token-level 或 TRL 默认层面的裁剪并不活跃，不能证明 sequence-level 更新一定健康，更不能证明 program 质量真的在持续改善。因此接下来的实验判断不能只盯着总 reward、KL 或 loss，而必须结合 verifier 指标一起看。对当前任务，真正关键的是程序可执行率、执行后答案正确率、程序结构得分、unique program ratio，以及 benchmark 里的 executed answer accuracy、program accuracy、pass@k 等结果。如果 sequence-level 训练让总 reward 稳定但程序可执行率下降，或者 exact match rate 上不去、benchmark 的 pass@1 不升反降，那就说明它并没有给当前任务带来实际增益。

整体上，这条 RL 主线可以用一句话概括：它不是在优化通用 CoT 写作能力，而是在把模型训练成一个更可靠的金融程序生成器。模型需要从金融文本和表格 prompt 中提取有效证据，生成形式正确、结构合理、可以被 executor 执行的 DSL 程序，并通过执行结果对齐 gold answer。GRPO 负责把这个目标拆成可观测的多项奖励，GSPO-compatible 负责把主要程序正确性信号压缩到 sequence-level core reward 中。后续所有较大改动，无论是 reward 重新配权、trainer objective 变化、日志协议扩充，还是 full GSPO loss 的真正实现，都应该继续先落到 `docs/plan` 再改代码，避免方法命名、实验口径和工程实现继续漂移。
