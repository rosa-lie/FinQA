# Distilling Reasoning Capabilities into Smaller Language Models

这篇论文讨论的是一个对 FinQA 十分现实的问题：如果大模型已经具备较强的逐步推理能力，如何把这种能力可靠地迁移到更小、部署成本更低的模型上。作者并没有简单模仿整条 CoT，而是提出 `Socratic CoT`，用问题分解和子问题求解的方式，把复杂推理拆成更适合小模型学习的结构。

论文摘要的大意是：逐步推理方法例如 CoT 对大模型非常有效，但其成功往往依赖于更大的参数规模。为此，作者提出一种知识蒸馏方法，将大模型的逐步推理能力蒸馏到小模型中。具体而言，论文引入 `Socratic CoT`，先把原问题分解成一系列子问题，再由专门模型逐个求解，最终形成可执行的推理协作过程。这样一来，复杂推理能力不再要求单个小模型一次性完成全部工作，而是通过组合方式获得。

在数据与任务设置上，这篇论文并不面向金融，而是面向一般复杂推理任务，但其方法与 FinQA 的结构非常相容。FinQA 本身就可以自然拆成若干子步骤，例如证据定位、变量抽取、公式组合、程序执行和答案生成。因此，这篇论文的真正价值不在数据集复用，而在于它提供了一种“如何拆分推理能力”的视角。

算法框架上，作者训练了两个小模型协同工作。一个模型负责问题分解，把原始复杂问题转化成更简单的子问题序列；另一个模型负责子问题求解，并利用这些子问题逐步推进最终答案。这种双模型结构与传统 CoT 的最大区别在于，中间推理被显式对象化，而不是全部隐含在一段自由文本里。对于 FinQA 来说，这几乎可以直接映射成“分解器 + 程序生成器”或“证据规划器 + 执行器”的设计。

实验部分显示，这种蒸馏路线能让小模型在复杂推理任务上明显优于直接模仿终答案或简单 CoT 的训练方式。作者用结果说明，推理能力本身也需要被结构化蒸馏，否则小模型很容易只学到表面叙述风格，而学不到真正的问题分解机制。这个结论与 FinQA 非常相关，因为 FinQA 的 gold program 和步骤监督本质上就属于结构化推理信号。

公开页面中没有看到一个广泛引用的官方 GitHub 仓库，因此这篇论文的复用重点更多在方法层而非具体代码。真正值得借鉴的是其“把大推理拆小、把隐式过程变显式模块”的思路，而不是某个固定脚本实现。

对于 FinQA，这篇论文提供了很有价值的复用方向。一个直接思路是把 FinQA 求解器拆成两个或三个轻量模块，例如先生成证据与操作规划，再生成可执行程序，最后由执行器验证答案。另一个思路是把大模型产生的优质 FinQA 过程数据拆成分解轨迹和子问题答案，分别蒸馏给不同子模块。这样做有望在较小参数规模下保留更多真正的推理结构，而不是只保留结果表面形式。

## ETD、CoT 与 PoT 在 FinQA 中的结合方式

如果进一步参考 `Ensemble Thoughts Distillation` 的思路，那么在 FinQA 中更合适的做法并不是让 `CoT` 和 `PoT` 各自独立地产生一套答案，再在最后阶段做简单拼接，而是把它们组织成分层协作的推理链。更具体地说，`CoT` 适合承担问题分解、证据组织、变量说明和步骤规划的职责，`PoT` 则适合承担关键数值计算、公式展开和程序执行的职责。这样一来，自然语言推理和程序化推理就不再是相互替代关系，而是前后衔接关系。对于 FinQA，这种结构尤其合理，因为很多错误并不是来自高层思路错误，而是来自变量绑定不稳、公式展开漂移或中间计算不可验证。

如果从数据构造的角度实现这一点，那么每一个训练样本最好都同时包含多种视角，而不是只保留单一路径监督。一个高质量样本可以被整理成 `question/context -> evidence -> short CoT plan -> PoT program -> final answer` 这样的链式结构。其中 `short CoT plan` 不需要追求很长，重点在于明确本题要抽取哪些证据、定义哪些变量、按照什么顺序进行推理；而 `PoT program` 则需要把真正的数值求解步骤落成可执行程序，例如 FinQA 的 operation sequence 或等价的 Python 程序。这样处理后，模型学习到的就不是“如何模仿一段像样的推理文字”，而是“如何先形成解题规划，再把规划翻译成可执行过程”。

在训练流程上，更稳妥的路线通常是分阶段蒸馏，而不是一次性把所有结构混在一起。第一阶段可以先训练模型生成较短的 `CoT plan`，重点建立问题分解和证据组织能力，让模型先学会如何阅读表格和文本、如何确定计算目标、如何定义中间变量。第二阶段再在这一基础上引入 `PoT` 监督，让模型学习把计划转成程序，并通过可执行程序得到最终答案。这样做的好处在于，小模型不会在一开始就同时面对“解释、规划、编码、计算、作答”五种任务压力，而是先收敛到较稳定的分解能力，再进一步学习程序化求解。

如果希望更贴近 `Socratic CoT` 的思想，那么整个系统甚至可以直接拆成两个轻量模块。第一个模块可以被看作“分解器”或“规划器”，负责输出简短、结构化、可复用的解题计划；第二个模块可以被看作“程序生成器”或“求解器”，读取这个计划后生成程序，再由执行器返回结果。对于 FinQA，这几乎可以自然映射成“证据规划器 + 程序生成器 + 执行验证器”的结构。与单模型直接输出长文本答案相比，这样的设计更容易控制中间过程，也更方便后续做错误定位和 reward 设计。

从 ETD 的视角看，真正有价值的不是简单地把 CoT 数据和 PoT 数据拼成更大的训练集，而是让同一个样本拥有互补的 reasoning view，然后以多任务方式共同蒸馏。因此，训练数据最好不是 `50% CoT 样本 + 50% PoT 样本` 这种粗糙混合，而是让每个高质量样本同时带有 `plan`、`program` 和 `answer` 三层信息。训练初期可以适度提高 `plan` 相关目标的权重，帮助模型先形成清晰的分解能力；中后期再提高 `program` 和 `execution-consistent answer` 的权重，使模型把关键数值步骤收敛到可执行表示上。这样才能真正体现 ETD 的“多种推理路径互补”。

在推理阶段，也可以把这种训练思路延续下去。一个更适合 FinQA 的解码流程是，先生成多个候选 `CoT plan`，再针对每个计划生成对应程序并执行，最后对执行结果而不是自然语言答案进行投票。这种方式的好处在于，表面上不同的计划或程序，只要执行结果一致，就可以在最终阶段形成稳定答案；反过来，如果某条路径的自然语言解释看起来合理，但程序不可执行或执行结果偏离，也可以被自动剔除。对 FinQA 这类数值任务而言，这种“按执行结果聚合”的机制往往比“按文本答案投票”的机制更可靠。

如果进一步考虑后训练或强化学习，那么奖励设计也应当和上述结构保持一致。比起奖励更长、更像人的 CoT 文本，更有效的方向通常是奖励 `计划是否合理`、`程序是否可执行`、`执行结果是否正确` 以及 `最终答案是否与标注一致`。其中，程序可执行性和执行正确率对于 FinQA 特别关键，因为它们能把推理过程从“看起来合理”转成“可以被验证”。因此，在当前项目中参考 ETD，并不意味着要把 CoT 和 PoT 简单叠加，而是意味着要把它们设计成一个从分解到执行再到验证的完整闭环。
